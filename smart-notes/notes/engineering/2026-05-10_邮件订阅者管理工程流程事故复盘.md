**关键问题：**
- 两个入口（飞书/网页）写**不同**的地方 → 多源写入 → 互相看不见

## 覆盖关系矩阵（Before）

| 操作 | 本地 Mac | Gitee | 腾讯云 |
|---|---|---|---|
| 飞书加人（我改本地+commit）| ✍️ 写 | ✍️ push | ❌ 被 git reset 覆盖（但被保护机制救了） |
| 网页加人（腾讯云 HTML）| 👻 看不见 | 👻 看不见 | ✍️ 写 |
| `deploy_sync.sh` （腾讯云每几小时跑）| — | 📥 fetch | ⚠️ git reset 会覆盖，保护机制兜底 |
| `sync_to_cloud.sh` （本地 17:50）| 📤 推 | — | ⚠️ rsync 但此文件已 exclude |

**核心问题一句话：**
> 两个入口写入目标不同，本地和腾讯云存在 git 层的双向危险同步，保护机制只是权宜之计。

## 保护措施（工程化而非靠记忆）

### 1. Hard Rule：文件永久从 git 移除
```bash
# .gitignore
/env_fit/momentum_stock/email_subscribers.json
# git rm --cached 已执行
```

### 2. AI 行为规则（写进 MEMORY）
> **飞书加/减订阅者 → AI 必须 SSH 到腾讯云改，禁止改本地文件。**
> 禁令：`git add -f email_subscribers.json` 是红线。

### 3. `deploy_sync.sh` 保留保护机制（防御纵深）
即使前两条失效，保护机制还能兜底。

### 4. 本地 Mac 永远不是真源
需要查看时 `scp`，不 commit，不 push。

---

## 推荐理由

1. **单一真源（Single Source of Truth）**  
   订阅者是**线上运营数据**，不是代码。线上系统（腾讯云）是它的天然归属。git 不应该管它。

2. **入口多但落点唯一**  
   飞书和网页两个入口最终都写到同一个物理文件。不存在"两个副本是否一致"的问题。

3. **工程化保证 > 记忆力保证**  
   今天的事故根因是"我忘了 05-08 的决策"。靠人/AI 记忆维持一致性，在用户上百、上千时必然出问题。v3 把规则落到：
   - `.gitignore`（机器强制）
   - `git rm --cached`（git 层强制）
   - MEMORY.md（我的行为约束）
   - `deploy_sync.sh` 保护机制（兜底）

4. **未来扩展到百/千人无压力**  
   订阅者再多，也只是一张 JSON 表，只在一台机器上。未来如果真的到上万人，再谈迁移到 Postgres + Admin API，但到那时架构本来就会升级（现在是数量问题，不是结构问题）。

5. **今天的事故是 v3 落地时的临时裂缝**  
   现在已经恢复两端都是 27 人、git 里没有这个文件。我只要把规则写进 MEMORY，v3 就正式生效。
